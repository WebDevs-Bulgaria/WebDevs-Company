# WebDevs-Company

Фирменият сайт на „Уеб Девс България“ ЕООД — домейн `webdevs.bg`.

Това е публичната част на по-голяма система. По-късно към нея се добавят клиентски портал със система за заявки, плащания и административен панел. Структурата по-долу е избрана така, че тези части да се добавят без пренаписване.

## Технологии

| Какво | Версия | Бележка |
|---|---|---|
| Next.js (App Router, Turbopack) | 16.4.6 | включени `cacheComponents` и `partialPrefetching` |
| React | 19.3 | |
| TypeScript | 5 | `strict` |
| Tailwind CSS | 4.3 | темата е в `src/app/globals.css`, няма `tailwind.config.js` |
| zod | 4 | проверка на данните от формата |
| next-i18next + i18next + react-i18next | 16.4 / 27 / 18 | преводите; ползват се само на сървъра |
| Node.js | ≥ 20.9 | разработвано на 26 |

> **Преди да пишете код:** тази версия на Next.js се различава от по-старите (вижте `AGENTS.md`). Актуалната документация е локално в `node_modules/next/dist/docs/` — четете оттам, не по памет.

## Пускане

```bash
npm install
npm run dev        # http://localhost:3000 — пренасочва към /bg или /en
npm run build      # production build
npm run start      # пуска production build-а
npm run lint
npx tsc --noEmit   # проверка на типовете (след build или `npx next typegen`)
npm run check:locales   # двата езика имат ли едни и същи ключове (пуска се и преди build)
```

### Променливи на средата

| Име | По подразбиране | За какво служи |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | `https://webdevs.bg` | основа за каноничните адреси, hreflang, sitemap и JSON-LD |
| `NEXT_PUBLIC_ALLOW_INDEXING` | не е зададена | само при стойност `true` сайтът се отваря за търсачките |

Без `NEXT_PUBLIC_ALLOW_INDEXING=true` всяка страница носи `noindex, nofollow`, а `robots.txt` забранява всичко. Това е нарочно: среда за преглед или локално копие не бива да бъде индексирано като дубликат на сайта. Променливата се задава **само** на истинския домейн.

### Защо е така

- **Група маршрути `(site)`.** Папка със скоби подрежда кода, без да влиза в адреса. Порталът и административният панел ще получат свои групи `(portal)` и `(admin)` със собствена рамка и проверка за вход, без да се пипа публичният сайт.
- **Сървърни компоненти по подразбиране.** Клиентски (`"use client"`) са само `MobileMenu`, `LanguageSwitcher` и `ContactForm`. Всичко останало се изпраща като готов HTML — това носи скоростта и видимостта в търсачките.
- **Слой за съдържание.** Страниците взимат съдържанието си от `src/lib/content/`, не направо от файловете с преводи. Когато дойде административният панел, се сменя само вътрешността на тези функции.
- **Преводите са с i18next (`next-i18next`).** Вижте раздела „Преводи“ по-долу.
- **Не е статичен експорт.** Страниците се генерират статично при build, но проектът остава пълно Next.js приложение, защото формата, а по-късно порталът, имат нужда от сървърен код.

## Как се добавя…

**…страница**
1. Добавете я в `sitePages` в `src/lib/site.ts` (ключ и път).
2. Добавете namespace файл за страницата на всеки език (или ключове в съществуващ) със `meta.title` и `meta.description`, името ѝ в `nav.<ключ>` в `common.json` и реда ѝ в `metaNamespace` в `src/lib/seo/metadata.ts`.
3. Създайте `src/app/[locale]/(site)/<път>/page.tsx` с `generateMetadata` → `buildPageMetadata("<ключ>")`.

Страницата влиза сама в `sitemap.xml`, във футъра и получава canonical и hreflang. В главното меню влиза, ако не е изключена в `navPages`.

**…текст.** В съответния namespace файл в `src/i18n/locales/bg/` **и** `en/`, с един и същ ключ. В компонента: `const { t: tHome } = await getT("home")` и `tHome("hero.eyebrow")`. Текст за потребителя не се вписва направо в компонент.

**…език.** Добавя се в `locales` и `localeTags` в `src/i18n/config.ts`, в `names` в `LanguageSwitcher.tsx` и се създава папка `src/i18n/locales/<език>/` със същите файлове като `bg/` (`npm run check:locales` показва какво липсва).

**…namespace.** Името му в `namespaces` в `src/i18n/settings.ts`, файл `<име>.json` във всяка езикова папка и ред в `src/i18n/i18next.d.ts`.

## Преводи

Преводите са с **i18next** през **next-i18next** (App Router). Текстовете са в `src/i18n/locales/<език>/<namespace>.json`.

| Namespace | Какво съдържа |
|---|---|
| `common` | навигация, бутони, футър, покана за връзка, ангажименти, 404, име на сайта |
| `home`, `services`, `solutions`, `about`, `contact`, `privacy` | по един на страница, с `meta.title` и `meta.description` |
| `admin`, `tickets` | **предвидени** за административния панел и системата за заявки; засега са празни (`{}`) |

**Как се ползва** (сървърен компонент):

```tsx
import { getT } from "@/i18n/server";

const { t } = await getT("common");
const { t: tHome } = await getT("home");

t("nav.services");        // текст
tHome("hero.eyebrow");
tServices("items");       // списък или обект — returnObjects е включено в settings.ts
```

- **Винаги подавайте име на namespace.** `getT()` без име дава на `t` твърде широк тип (всички namespace-и наведнъж) и TypeScript спира да различава текст от обект.
- **По една функция на namespace** (`t`, `tHome`, `tServices`…), а не префикс в ключа (`"home:hero.title"`) — типовете на библиотеката не приемат префикса.
- **Езикът идва от адреса** (`next/root-params`), затова страниците остават предварително генерирани. В Server Action и в `global-not-found.tsx` адрес няма: `getT("contact", { lng: locale })`.
- **Клиентските компоненти не ползват i18next.** `ContactForm`, `MobileMenu`, `LanguageSwitcher`, `ThemeToggle` и `PaletteSwitcher` получават готовите текстове като свойства от сървърния компонент над тях. Така в браузъра не отива нито ред от библиотеката (проверено: JS към браузъра е 708 KB в 13 файла и преди, и след въвеждането ѝ; Lighthouse остава 100). Ако някой ден клиентски компонент има нужда от `useT()`, трябва `I18nProvider` в root layout-а — това ще добави кода на i18next към всяка страница; измерете преди и след.
- **Пренасочването по език** е собственият `src/proxy.ts`, не `createProxy` на библиотеката: нашият не записва бисквитка (в политиката за поверителност пише, че сайтът не ползва такива).
- **Проверка на ключовете:** TypeScript проверява ключовете в `t()` спрямо българските файлове (`src/i18n/i18next.d.ts`); `npm run check:locales` проверява, че останалите езици имат същите файлове и ключове, и се пуска автоматично преди `npm run build`.
- **Множествено число и стойности в текста** (за портала): `"requests_one": "{{count}} заявка"`, `"requests_other": "{{count}} заявки"` и `t("requests", { count })`.


## SEO

- **Мета данни:** `buildPageMetadata()` връща за всяка страница уникално заглавие и описание, каноничен адрес, hreflang връзки между езиците (`bg-BG`, `en`, `x-default` → български) и данните за споделяне.
- **`/sitemap.xml`:** всяка страница на всеки език, с връзки към другите езикови версии.
- **`/robots.txt`:** зависи от `NEXT_PUBLIC_ALLOW_INDEXING` (вижте по-горе).
- **JSON-LD:** `ProfessionalService` с данните от `src/lib/company.ts` и каталог на услугите, `WebSite`, а на вътрешните страници — `BreadcrumbList`.
- **Пренасочване:** адрес без езиков префикс отива към `/bg` или `/en` според езика на браузъра. Ботовете обикновено не пращат езикови предпочитания и попадат на `/bg`; двете версии са достъпни направо и са в sitemap.

## Страници на услугите

- Адрес: `/<език>/services/<id>`, файл `src/app/[locale]/(site)/services/[service]/page.tsx`. Списъкът на id-тата е в `src/lib/services.ts` (взима се от `locales/bg/services.json`).
- Съдържанието е в `items[]` в `services.json`: `summary`, `intro`, `points` (какво включва), `suitable` (кога е подходяща), `result` (какво получавате).
- **Пътят горе** е от три нива — „Начало / Услуги / името на услугата“ — и „Услуги“ е връзка (`PageHeader` с `current`). Преди беше от две нива и „Услуги“ беше текст, та от услуга не можеше да се върнеш към списъка. Същите три нива са и в `BreadcrumbList` (`breadcrumbJsonLd("services", leaf)`). Шрифтът на пътя е 12px, на широк екран (lg) 15px.
- Накрая е формата за запитване със скрито поле `service`; действието приема само познати id-та.
- `export const instant = false` е нарочно: всички услуги се генерират при build. Не слагайте `params` в `<Suspense>`, за да „оправите“ предупреждението.
- Несъществуваща услуга връща истински 404 от `src/proxy.ts` (пренаписва адреса към несъществуващ път). `notFound()` в самата страница не стига: страницата е частично предварително генерирана и отговорът тръгва със статус 200.
- Нова услуга: запис в `items` на `services.json` и в двата езика; адресът, картата на сайта и JSON-LD я поемат сами.
- **Групи:** `ai`, `websites`, `applications` — в този ред се показват навсякъде; AI е първа нарочно, с нея сайтът се отличава (решение от 13.11.2026). Редът идва от `serviceGroups` в `src/lib/content/index.ts`). Името на групата е едновременно котва в „Услуги“ (`/services#ai`), ключ в `services.json → groups` и ключ в `home.json` (надписът над заглавието). Нова група иска запис на трите места. Заглавието на групата трябва да е кратко — стои в колона, широка 22rem („AI и автоматизация“ не се побра, затова е „AI решения“).
- **Въведение от няколко абзаца:** `intro` се дели на абзаци по празен ред (`\n\n`) в превода; така страницата на WordPress има втори абзац за AI.
- **Цени:** всяка услуга има поле `price` — готов текст („от 1 200 €“, „по оферта“), не число. Показва се в реда на услугата (`ServiceRows.tsx`) и в лявата колона на страницата ѝ. Числата не се смятат никъде; при смяна на цена се пипа текстът на двата езика.

## Цени на началната страница

- **„Цени“ в менюто** не е страница, а връзка към секцията `#prices` на началната (`Header.tsx`, надпис `nav.prices`). Затова я няма в `sitePages`, в картата на сайта и във футъра.
- **„За кого е“** (`home.json → audience`) стои над цените; накъде води всяка ситуация, е в `audienceLinks` в `page.tsx` (ключът е `id`).
- **Въпросите** (`home.json → faq`, секция `#faq`) са `<details>` без JavaScript и излизат и като структурирани данни `FAQPage`. В отговорите има срокове и цени (40 € и 39 € на месец) — при смяна на цена се поправят и тук.

- Секцията „Три начина да започнем“ (`#prices`) в `src/app/[locale]/(site)/page.tsx` чете `home.json → packages`: три линии — `quick-start` (WordPress), `custom` (програмирано по поръчка, водещата) и `ai`. Те не са стъпала по бюджет, а три отделни пътя; `custom` е отбелязана с надписа от `packages.badge`.
- Накъде води всяка линия, е в `packageLinks` в същия файл (ключът е `id` на линията). Нова линия без запис там води към „Услуги“.
- Цените в `packages.items[].price` повтарят най-ниските цени от `services.json` — при промяна се сменят и на двете места.
- Лентата „AI“ стои веднага под движещата се лента, преди „Сайтове“ и „Софтуер по поръчка“ (номерата 01–03 в надписите са написани на ръка в страницата). Тя е с фон `brand-gradient` и бял текст. `--brand-from/--brand-to` са подбрани да държат контраст с бяло във всички палитри; нова палитра се проверява и тук. Потъмняването вдясно (`to-black/30`) не е украса: без него белият текст върху тюркоазения край на градиента е с контраст около 3,2:1.

## Форма за контакт

- Компонент: `src/components/sections/ContactForm.tsx`. Сървърна част: `src/lib/actions/contact.ts`.
- Проверката на данните е на сървъра (zod). Атрибутите `required` в HTML са само удобство.
- Защита от спам: скрито поле-капан `website` и ограничение до 5 запитвания за 10 минути от един адрес.
- Работи и при изключен JavaScript.
- **Бюджет и срок** (`budget`, `timeline`) са падащи списъци по избор. Възможностите са в `contact.json → form.budgetOptions / timelineOptions`; ключът (`500-1500`, `one-month`) е това, което се изпраща, а текстът е само за показване. Сървърът приема само ключ, който съществува в превода — всичко друго става „не е избрано“. Нова възможност = нов ключ на двата езика, код не се пипа. Добавите ли ново поле с лични данни, допълнете и раздел „Какви данни събираме“ в `privacy.json`.
- **Изпращането на имейл още не е настроено.** `sendContactMessage()` при разработка извежда запитването в конзолата на сървъра и връща успех; в production хвърля грешка и потребителят вижда съобщение да пише на имейла. Услугата се избира заедно с хостинга — сменя се само тази функция.

## Палитри

- **Къде се избират:** на широк екран — кръгче с цвета на избраната палитра в шапката, което отваря малък панел; на тесен — ред „Цветове на сайта“ в мобилното меню. Един компонент, `PaletteSwitcher`, с `variant="popover"` и `variant="inline"` (`Header.tsx`; в `MobileMenu` влиза през `extra`). До 13.11.2026 беше плаващо хапче долу вдясно — махнато е, защото закриваше съдържание на телефон, а ъгълът е за AI асистента.
- Списъкът е в `src/components/theme/palettes.ts`, цветовете — в блоковете `:root[data-palette="…"]` в `src/app/globals.css`, имената — в `common.json → nav.palette` (и се подават в `(site)/layout.tsx`). Нова палитра иска запис на четирите места.
- **По подразбиране е `orange`** (`defaultPalette`, от 13.11.2026; преди това `turquoise`). Посетител, който вече е избирал палитра, запазва своята — ключът в `localStorage` (`wd-palette-2`) не е сменян нарочно.
- **`orange` и `multicolor` са пробни** (фаза 2, етап 3, 13.11.2026). Ако някоя отпадне, маха се от четирите места; запазен избор на посетител с изтрита палитра се пренебрегва сам (ThemeScript приема само имена от списъка).
- **Глобусът има собствени цветове** `--globe-from / --globe-mid / --globe-to`. По подразбиране са цветовете на палитрата; пробните ги задават отделно, защото яркото оранжево (#ff5a14) не държи контраст като текст и под бял текст и не може да е `--color-accent`.
- **`.hue-cycle`** върху списък (`ul`, `ol`, `dl`) значи: при `multicolor` всяко пряко дете получава поред един от пет акцента (оранжево, червено, синьо, тюркоазено, розово-лилаво) чрез смяна на `--color-accent`, `--color-brand-2`, `--brand-from/to` и `--color-night-accent` за целия елемент. В другите палитри класът не прави нищо. Работи само върху преките деца — обвиете ли елементите в допълнителен `div`, редуването спира.
- Всеки нов цвят за текст се проверява за контраст 4,5:1 върху `canvas` и върху `surface`, а `--brand-from/to` — под бял текст.

## AI асистент (засега само мястото)

- `src/components/assistant/AssistantOrb.tsx` — плаващ бутон долу вдясно на всяка страница (слага се в `(site)/layout.tsx`). **Асистентът още не съществува:** при натискане се отваря панел „Скоро“ с връзка към „Контакт“ (текстове: `common.json → assistant`). Когато асистентът стане готов, се заменя съдържанието на панела; бутонът, мястото и размерите остават.
- `src/components/visuals/LivingOrb.tsx` — самото „живо“ кълбо: само `span`-ове и CSS (`.living-orb` в `globals.css`), без JavaScript и без картинки. Три размазани петна се движат в стъклена сфера с различна скорост (7, 9 и 11 s, затова не се повтарят заедно), ядрото бие като сърце, цялото диша и леко мени формата си. Всички размери са в проценти — кълбото се мащабира от `className` (36px в примерния разговор, 56–64px за бутона). Цветовете са `--globe-*`, тоест следват палитрата.
- При посочване и докато панелът е отворен, петната и ядрото се забързват (`.living-orb-button`). При „намалено движение“ в системата всичко стои неподвижно (общото правило в края на `globals.css`).
- **Примерният разговор** в групата AI на „Услуги“ (`.chat-demo`, текстове `services.json → groups.ai.demo`) е проба за „живи образи“: без анимация се вижда готовият отговор, точките „пише“ са скрити по подразбиране.
- Ако на хостинга има значка долу вдясно (безплатният план на Netlify), тя ще се застъпи с кълбото.

## Капани

- **След промяна в `globals.css` dev сървърът не зарежда новите стилове** — нови класове изглеждат като елементи с нулев размер. Спира се сървърът, трие се `.next`, пуска се наново. Ако веднага след пускането няколко отворени раздела поискат страници едновременно, може да излезе `SyntaxError: Unexpected non-whitespace character after JSON` и всичко да връща 500 — пак спиране, триене на `.next` и пускане.

- **`ThemeScript` пази `data-theme` и `data-palette` с MutationObserver.** При смяна на езика React маха и слага наново атрибутите на `<html>` със стойностите от сървъра (`data-theme="light"`); наблюдателят ги връща към избора на посетителя в същата задача, преди да се нарисува кадър. Затова всеки код, който сменя темата или палитрата, **първо записва в `localStorage`, после сменя атрибута** — в обратния ред наблюдателят връща старата стойност. Бутонът на плъзгача нарочно няма `transition` на цветовете.
- **При смяна на езика страницата се монтира наново** (езикът е параметър на root layout-а) и анимациите при появяване тръгват пак — съдържанието изчезва и „присветва“. `LanguageSwitcher.tsx` слага `data-lang-switch` на `<html>` при натискането и отново, когато новият език е на екрана; докато го има, `.rise-in` е изключена (`globals.css`). Атрибутът се маха чак при преминаване към друга страница: махне ли се по-рано (например с таймер), анимацията тръгва в същия миг. Нова анимация при зареждане трябва да се изключи по същия начин.
- **Кръгчето на плъзгача за темата се анимира само след натискане** (`data-animate` на бутона в `ThemeToggle.tsx`). При смяна на езика React презаписва атрибутите на `<html>` и `data-theme` минава за миг през `light`; с постоянен `transition` кръгчето се местеше видимо. Не връщайте постоянния `transition`.
- **Лентата с технологии повтаря съдържанието четири пъти** и се измества с една четвърт (`translateX(-25%)`). С две копия на екран, по-широк от едно копие (около 1540 px), вдясно оставаше празно и лентата видимо скачаше в началото. При промяна на броя копия сменете и процента.
- **Ефектите при посочване не бива да променят размери** (отстъп, ширина, шрифт): текстът се пренася и страницата подскача. Ползвайте `transform` (`translate`, `scale`).
- **Не връзвайте Server Action с `.bind()` в клиентски компонент, който ползва `useActionState`.** В Next.js 16.4.6 това блокира целия сървър, когато формата се изпрати без JavaScript: заявката не получава отговор и процесът спира да обслужва всички останали заявки. Възпроизведено и в `next dev`, и в `next start`. Затова езикът се подава на действието със скрито поле `locale`, а не с `bind`. Преди да върнете `bind`, проверете с изключен JavaScript.
- **Не извиквайте `new Date()` или `Math.random()` в сървърен компонент** без кеширане — при `cacheComponents` това проваля статичното генериране. Затова във футъра няма година.
- **Обектът `openGraph` на страница замества наследения**, включително картинката от `opengraph-image.tsx`. Затова `buildPageMetadata()` посочва картинката изрично.
- **Нов компонент се проверява и в двете теми.** Ползвайте цветовете от темата (`text-ink`, `bg-surface`…), не `text-white`/`bg-white`, освен върху `.brand-gradient`. За фон с градиента на марката е `--brand-from/--brand-to`, за текст и икони — `--color-accent`/`--color-brand-2` (в тъмната тема са по-светли).
- **Страницата „Услуги“ има две залепващи ленти** — шапката (4.5rem) и лентата с връзки под заглавието. Затова котвите там са с `scroll-mt-32` (секции) и `scroll-mt-40` (редове), а залепващите заглавия — на `top-40`. При нова котва на тази страница ползвайте същите стойности, иначе заглавието остава скрито под лентите.
- **Надписите са с различна дължина на различните езици.** Шапката е решетка `1fr auto 1fr`, бутонът за връзка е с постоянна ширина, а превключвателите са с постоянни размери — иначе елементите се местят при смяна на езика. При нов елемент в шапката проверете и `/bg`, и `/en`.
- **`ThemeScript` вмъква скрипта с `useServerInsertedHTML`, а не като `<script>` в JSX.** При смяна на езика root layout-ът се рисува в браузъра и React дава грешка за script таг в компонент.
- **Не махайте `suppressHydrationWarning` от `<html>`.** `ThemeScript` сменя `data-theme` преди React да се зареди; без него React отчита разминаване.
- **Анимации:** `.rise-in` (появяване при зареждане, закъснение през `--delay`) и `.reveal` (появяване при скрол, само където браузърът поддържа `animation-timeline: view()`). Не слагайте съдържание, което е невидимо без анимацията — в браузър без поддръжка `.reveal` не прави нищо, а при „намалено движение“ всички анимации са изключени.
- **Залепващо заглавие (`position: sticky`) не работи в секция с `overflow-hidden`.** Секциите с образ зад съдържанието ползват `overflow-clip` — отрязва по същия начин, но не прави секцията скролиращ контейнер.
- **`.brand-gradient` е по-силен от помощните класове на Tailwind** (дефиниран е извън слоевете), така че `bg-none`/`bg-*` върху него не действат. Ако фонът трябва да се сменя при посочване, ползвайте помощен клас (`bg-accent`), не `.brand-gradient`.
- **Промяна в `globals.css` не се презарежда от `next dev`** (нито `@theme`, нито нови правила и `@keyframes`). Сървърът продължава да сервира стария CSS: спрете го, изтрийте `.next` и го пуснете отново.
- **Шрифтовете се зареждат с `subsets: ["latin", "cyrillic"]`.** Без `cyrillic` английската версия изглежда добре, а българската пада на резервен шрифт.
- **`global-not-found.tsx` не минава през layout-ите.** Сам зарежда `globals.css` и шрифта; промяна по темата трябва да се провери и там. Флагът `experimental.globalNotFound` е в `next.config.ts`.
- **`overrides` в `package.json`** вдига `minimatch` на 11 за `@typescript-eslint/typescript-estree` (уязвимост GHSA-g3hv-75wg-m249, която `npm audit fix` не може да поправи сам). Когато `typescript-eslint` премине към безопасна версия, записът се маха.
- **Ограничението на честотата за формата е в паметта на процеса.** При повече от един сървър ще трябва общо хранилище.

## Състояние

Направено: скелет, два езика, страници (вкл. отделна страница за всяка услуга със запитване), SEO слой, форма за контакт, светла/тъмна тема и три палитри. Дизайнът е одобрен на 11.11.2026. Проверено върху production build: Lighthouse (мобилен профил) — 100 на скорост, достъпност, добри практики и SEO на шест страници (при `NEXT_PUBLIC_ALLOW_INDEXING=true`); контраст (axe-core) — без нарушения в двете теми и трите палитри.

Дизайн: етап 1. Светла и тъмна тема по избор на посетителя — атрибут `data-theme` на `<html>`, плъзгач `components/theme/ThemeToggle.tsx`, скрипт без премигване `components/theme/ThemeScript.tsx`; при първо посещение се следва устройството, изборът се помни в `localStorage` (`wd-theme`). Цветовете и сенките са в `src/app/globals.css`. Посетителят избира и цветова палитра — атрибут `data-palette`, превключвател `components/theme/PaletteSwitcher.tsx` долу вдясно; списъкът е в `components/theme/palettes.ts` („emerald“, „turquoise“, „violet“, пробните „orange“ — по подразбиране от 13.11.2026 — и „multicolor“; подразбирането е `defaultPalette` и се слага от root layout-а като `data-palette` на `<html>`, а „emerald“ са стойностите от `@theme` без собствен блок), имената — в `nav.palette` в речниците, цветовете — в блоковете `:root[data-palette=…]` на `globals.css`. За нова палитра се добавят и трите, шрифтовете (Manrope, Inter, JetBrains Mono с кирилица) — в `src/app/fonts.ts`. Образите са абстрактни и се генерират с код, без картинки (`src/components/visuals/`): `RibbonField.tsx` — светлинни ленти (горната част на страниците и поканата) `NodeGraph.tsx` — мрежа от точки и връзки (панелът и секцията за приложенията) и `WireSphere.tsx` — въртящ се глобус от линии (горната част на началната; въртенето е `scaleX` на окръжности с изместване във времето, без 3D). И двата са SVG, изчисляват се на сървъра и следват палитрата и темата през CSS променливите. В `NodeGraph` числата са псевдослучайни с фиксирано начало — `Math.random()` би дал разминаване между сървъра и браузъра.

Стилът е „остри форми и линии“: `rounded-sm`, тънки `border-line` вместо карти и сенки, едри заглавия, моноширинни надписи, номерация. Услугите се показват с `components/sections/ServiceRows.tsx`.

Началната страница е кратък вход: заглавие с глобуса, разделена секция на цяла ширина с по едно изречение за двете дейности (светла и тъмна половина), „Какво получавате“ и бързи връзки към „Решения“, „Технологии“ и „За нас“ — без списъци с услуги и без процеса. Подробностите стоят само на едно място — услугите и процесът в „Услуги“, технологиите в „Решения“, ангажиментите и принципите в „За нас“ — и не се повтарят на началната.

Позициониране: основната услуга е изработката на сайтове, приложенията са втора линия. Услугите са в две групи (`websites`, `applications`) — полето `group` на всяка услуга в `src/i18n/locales/<език>/services.json`; редът на групите е в `serviceGroups` в `src/lib/content/index.ts`.
